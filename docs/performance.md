# Website performance baseline

The baseline records HTML, JavaScript, CSS, and other asset bytes and local browser timings for `/reference/language/` and `/playground/`. Run it after a production build with `pnpm run build && pnpm exec playwright install chromium && node scripts/measure-performance.mjs`. The script starts a fresh Astro preview server, opens each page in a fresh Chromium context, totals same-origin response bodies, then runs the Playground starter program twice and waits for its rendered output. It separately opens Search to measure Pagefind's on-demand downloads. The compressed `mcl.wasm.gz` file is included in the assets fetched after the Playground first runs.

Baseline captured on 2026-10-22 from a local Apple Silicon macOS machine with Node.js 26.8.2 and Chromium 156.0.8078.4. The preview server was freshly started for this run. Asset totals are response body bytes and do not include HTTP headers; the WASM asset is the compressed file served by the site. `firstContentfulPaintMs`, `largestContentfulPaintMs`, and `cumulativeLayoutShift` are browser API proxies sampled 200 ms after page load, not a complete Web Vitals measurement session. Timings are single-run observations and depend on the machine, browser cache state, and load, so they are diagnostic values rather than acceptance thresholds.

The docs page does not load WASM or create a CodeMirror editor. Its Search interaction loads 155,440 bytes of Pagefind resources, including Pagefind's own 68,199-byte search WASM. This records search startup downloads, not query latency. The Playground creates a CodeMirror editor without loading MCL WASM; execution loads the 19,598,893-byte compressed MCL runtime and took 827 ms through the first rendered output. Its second execution took 38 ms. Assets observed after execution totaled 19,944,790 bytes, including runtime and JavaScript fetched after the navigation snapshot. `previewReadyMs` was 522 ms in this run. The isolated cancel interaction returned the UI to the Run button in 33 ms while a held WASM request was pending; this is a UI cancellation proxy, not a general compute cancellation benchmark.

The browser script loads two 15.9 MiB binary files and a `main.mcl` entrypoint through the folder input. Binary files are kept as `Uint8Array` values and transferred to the Worker using fresh copies, so repeated renders retain the project's source buffers. The latest run accepted 33,344,717 bytes in 67 ms and rendered successfully in 512 ms. This measures project import and evaluation, not peak memory usage.

Browser `performance.memory` is Chromium-specific and excludes important worker, WebAssembly, and process memory, so it does not provide a comparable peak-memory result. The browser script does not measure a production CDN, edge compression, real user devices, a full Web Vitals session, or a performance budget.
