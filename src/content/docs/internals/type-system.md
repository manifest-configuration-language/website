# 型解析と型付き中間表現

MCLは構文解析後に型定義を解決し、式の型と静的に分かる性質を解析します。評価器は、型検査済みの式を型付き中間表現へ変換できる場合、その表現を使って処理します。言語で利用できる型注釈や型エラーの意味は[型](/reference/types/)を参照してください。

## 型定義の解決

Parserは型注釈を`syntax.TypeExpr`として保持します。Engineはそれを`ResolvedType`へ変換し、組み込み型、型エイリアス、型パラメーター、List、Map、Union、Record、関数型を表現します。Recordは宣言済みのfieldと、追加propertyを許可するかどうかを持ちます。fieldごとのoptional指定も解決済み型に保持されます。

モジュール内の型定義は使用前に集められ、型パラメーターと参照先を検査します。循環する型エイリアスは拒否します。JSON Schemaを参照する型は、プロジェクトファイルシステムからSchemaを読み込み、モジュールごとのSchema IDを付けて検証に利用します。型スコープとSchemaは`TypeAnalysisContext`に登録されるため、後から実行時検証するときも宣言元の定義を参照できます。

## 静的型解析

式の解析結果は`TypeAnalysis`です。ここには推定された`ResolvedType`と、型だけでは表現できない静的情報を持つ`TypeAnalysisFacts`が含まれます。Factsは、既知の文字列定数、Record fieldやList要素に対応する解析結果、値がManifest bundleかどうか、置換後の型、関数本体の推論情報などを保持します。

Engineは変数の型とFactsを式に沿って伝播します。条件式の各分岐は条件によって絞り込まれたbindingで解析し、分岐結果の型とFactsを結合します。Optional fieldの参照、null合体、ListやMapのアクセス、組み込み関数もそれぞれの規則で解析します。情報を確定できない式では未知として扱い、推測した型を確定情報として報告しません。

型の互換性判定では型エイリアスを解決し、Unionの選択肢、Recordのfield、ListやMapの要素型、関数の引数と戻り値を比較します。`Any`を含む式など、静的に互換性を確定できない場合は「不一致」と断定せず、判定不能として扱います。実行時に検証が必要な型注釈は、実際の値に対する型検査で確認します。

## 型付き中間表現

型付き中間表現は、評価対象の式を専用のkindとoperatorで表し、型検査済みの型、元ソースのspan、必要な静的Factsを保持します。loweringは構文ASTと解析結果の両方を確認し、対応する式とoperandの型が確定している場合にのみ成功します。loweringできない式は既存の評価経路で処理されます。

Typed IRの評価器は、構文ASTのnode種別や演算子文字列を実行時に再解釈しません。演算子の動作はTyped IRのoperatorに対応する処理で決まり、式の評価中に型検査済みの型情報を利用します。エラーには元ソースのspanを付けるため、診断位置を保持したまま解析、型検査、評価を接続できます。

評価時にも検査が必要な型は、RuntimeValueに対して確認します。JSON Schema型は値をJSON表現へ変換してSchemaを検証し、通常の型はResolvedTypeの構造と値のkindを比較します。これにより静的解析で確定できるエラーは早期に報告し、実際の値が必要な検査は評価時に行います。
