# Website performance baseline

Run `pnpm run build && pnpm exec playwright install chromium && node scripts/measure-performance.mjs` after a production build. The script starts an Astro preview server behind a local HTTP proxy, opens `/reference/` and `/playground/` in fresh Chromium contexts, measures the first Pagefind search for `型`, runs the Playground twice, measures cancellation UI response, and renders a project with two 15.9 MiB binary files. The proxy serves the fingerprinted WASM from the production build with `Content-Type: application/wasm` and `Content-Encoding: gzip` on the same origin, so Chromium uses `WebAssembly.instantiateStreaming` with HTTP decompression. The worker bundle is instrumented in the test context to time that call and inspect the exported Go WASM memory. The script also records the maximum Event Timing duration among its synthetic page interactions.

Baseline captured on 2026-10-22 from a local Apple Silicon macOS machine with Node.js 26.8.2 and Chromium 156.0.8078.4. Asset totals use response body bytes and exclude HTTP headers. The Playground downloads the fingerprinted 19,598,887-byte gzip WASM asset only when the user runs MCL. Timings are single-run observations affected by machine load and browser state; they are diagnostic values, not acceptance thresholds.

| -------------- | -----------: | -----------------: | ----------: | ------------: | --------------: | --------: | --------: | --------: | --------------------: |
| `/reference/`  | 27,604 bytes |      102,158 bytes | 68,074 bytes |       0 bytes |           61 ms |     48 ms |     64 ms |         0 |                40 ms |
| `/playground/` | 29,678 bytes |      625,989 bytes | 68,074 bytes |       0 bytes |           34 ms |     24 ms |     36 ms |    0.0523 |                32 ms |

The reference page does not load MCL WASM or create a CodeMirror editor. The first search for `型`, including opening Search and waiting for the first visible Pagefind result, took 867 ms and loaded 209,484 bytes of on-demand assets. This includes Pagefind's 68,199-byte WASM file and result fragments. The Playground creates CodeMirror without loading MCL WASM. Its first execution, including Worker startup, WASM transfer, runtime startup, and rendering, took 827 ms; the second took 37 ms. The `WebAssembly.instantiateStreaming` call took 132 ms from invocation until its promise resolved. That interval includes any remaining streamed response transfer as well as WebAssembly compilation and instantiation; it is not a compile-only duration. After execution, the Worker and WASM assets totaled 19,935,797 bytes, including the 336,910-byte Worker bundle with `wasm_exec.js`.

The project-import run accepted 33,344,717 bytes across three files in 70 ms and rendered in 490 ms. The cancel interaction returned the UI to the Run button in 34 ms while the compressed WASM request was held. This measures UI response, not worker computation time.

The Chromium Event Timing API observed one interaction on the reference page and two on the Playground. The largest individual event durations were 40 ms and 32 ms, respectively, both for `pointerdown`. This maximum is a lab interaction proxy from this script's small, synthetic interaction sample. It is not field INP and does not compute the 98th percentile across real visits. Entries shorter than 16 ms are not reported by the browser observer.

The Go WebAssembly module's exported `mem.buffer.byteLength` was 49,545,216 bytes immediately after instantiation, 88,670,208 bytes after the first render, and 140,247,040 bytes after rendering the 31.8 MiB binary project. These values are the current capacity of the WASM linear memory, not the number of bytes actively used by Go, resident physical memory, or total browser memory. They exclude JavaScript heap, DOM, browser process overhead, and other worker allocations. WebAssembly memory grows but does not shrink, so the last value is the largest linear-memory capacity reached in that run; it is not an overall browser peak-memory measurement.

The pull request, push, scheduled, and manual GitHub Actions workflows compare four response-body byte totals against limits in [`scripts/performance-budget.json`](../scripts/performance-budget.json). Each limit is 15% above the corresponding local baseline in the table and the descriptions above: 227,512 bytes for initial `/reference/` assets, 832,303 bytes for initial `/playground/` assets, 240,907 bytes for the first search's on-demand assets, and 22,926,167 bytes for assets loaded by the first Playground execution. These aggregate byte counts are the only enforced budgets. The performance workflow records the measurements and pass/fail result in its summary and fails when any total exceeds its limit. The website CI runs the same check after its browser E2E suite. Update the limits and this documentation when an intentional asset change establishes a new baseline. Timing, memory, and interaction measurements remain diagnostic values and do not gate CI.

The results do not measure a production CDN, real user devices, or a field Web Vitals session.
